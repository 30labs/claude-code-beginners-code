  1. A CSV problem crashes the CLI with a traceback

  read_entries (ledger.py:20) does no validation, and main
  (tally.py:73) catches nothing. That's inconsistent with
  --month, --top and --rules, which all fail cleanly with exit
  code 2. The CSV is the input most likely to be messy, yet it's
  the only one without that handling:

  ┌─────────────────────┬───────────────────────────────────┐
  │        Input        │              Result               │
  ├─────────────────────┼───────────────────────────────────┤
  │ Path that doesn't   │ FileNotFoundError traceback       │
  │ exist               │                                   │
  ├─────────────────────┼───────────────────────────────────┤
  │ UTF-8 BOM at the    │ KeyError: 'date', because the     │
  │ start (common in    │ header is read as \ufeffdate      │
  │ bank exports)       │                                   │
  ├─────────────────────┼───────────────────────────────────┤
  │ Amount written as   │ decimal.InvalidOperation          │
  │ "1,234.00"          │ traceback                         │
  ├─────────────────────┼───────────────────────────────────┤
  │ Bad date, a short   │ ValueError, AttributeError or     │
  │ row, or a missing   │ KeyError traceback                │
  │ column              │                                   │
  ├─────────────────────┼───────────────────────────────────┤
  │ Amount of NaN       │ Loads fine, then crashes when     │
  │                     │ compared with > 0 in totals       │
  └─────────────────────┴───────────────────────────────────┘

  None of these cases are tested. Reading the file with
  encoding="utf-8-sig" alone would fix the BOM case.

  2. Amounts print exactly as the CSV wrote them

  Amounts are never rounded to 2 decimal places. Decimal keeps
  whatever precision the file uses, and the >10 format just
  displays it. Running the CLI on a file with 3200, 18.9 and
  this never shows up. The same fixed-width formatting has a
  related gap: a description longer than 20 characters isn't
  truncated, so it pushes the amount column out of line.

  3. Rule matching only splits on spaces

  categorise (ledger.py:64) uses description.split(), which
  splits on whitespace only. So Corner Market, Leeds doesn't
  match Market (the word becomes Leeds's neighbour Market, with
  the comma attached), and METRO-CARD doesn't match Metro. With
  the sample rules.toml, both went to uncategorised. Real bank
  descriptions are full of commas, hyphens, slashes and
  reference numbers, so a lot of spending will probably end up
  uncategorised without any warning. The tests only use
  descriptions separated by spaces. There's also a smaller gap:
  read_rules accepts both Market and market as separate keys,
  and the second one can never match, because the first rule
  related gap: a description longer than 20 characters isn't
  truncated, so it pushes the amount column out of line.
